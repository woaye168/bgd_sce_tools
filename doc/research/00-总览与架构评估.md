# 00 — BGD SCE 技术生态总览与架构评估

> 评估日期：2026-08-20
> 本报告是五仓库源码级审查的总览篇，基于前置报告 [01-宿主工具评估](01-宿主工具评估.md)、[02-Lua框架评估](02-Lua框架评估.md)、[03-应用生态评估](03-应用生态评估.md) 与 [04-跨仓库一致性与流程评估](04-跨仓库一致性与流程评估.md) 的事实汇总而成；流程类结论均在 04 中经过文件级核实。

## 1. 五仓库定位与协作关系

```
                        ┌──────────────────────────────────────────┐
                        │  bgd_sce_tools（宿主，Tauri 2 GUI + CLI） │
                        │  项目初始化 / 构建 / 监听 / 框架更新 /     │
                        │  应用市场 / 自我更新                      │
                        └───────┬──────────────────┬───────────────┘
              框架下发/增量更新 │                  │ 应用分发（registry → app-release.json → asset）
                                ▼                  ▼
                ┌───────────────────────┐   ┌─────────────────────────────┐
                │ bgd_sce_framework     │   │ bgd_sce_plugins (= appsdk)  │
                │ Lua 框架模板（template/│   │ 双职责：registry.json 清单   │
                │ .bgd/{libs,src}）      │   │ + Rust crate bgd_appsdk     │
                └───────────┬───────────┘   └──────────────┬──────────────┘
                            │ 构建期改写注入                │ crates.io: bgd_appsdk = "0.1"
                            ▼                              ▼
                ┌───────────────────────┐   ┌──────────────┴──────────────┐
                │ 游戏项目（.bgd/ + 引擎 │   │ sce_app_visual-injector     │  sce_app_editor-patch
                │ 目录产物）             │   │ 扫描 .bgd api/ Lua 模块 →   │  编辑器整库解密/插槽/补丁模块
                └───────────────────────┘   │ 触编 JSON + SceInit.lua     │  C# MCP 桥（进程内注入）
                                            └─────────────────────────────┘
```

- **宿主 → 框架**：init 时下载 framework main 快照渲染到项目 `.bgd/`；后续以三路哈希增量更新（只碰 `libs/`，冲突保留本地另存 `.framework-new`）。
- **宿主 → registry → 应用**：registry.json（极简 id/name/repo）→ 各应用仓库 Release 的 `app-release.json` 补全版本/描述/版本说明 → 按 `asset_name` 下载 exe 安装到 `apps/<id>/`；启动透传 `--project-path` / `--background`，退出广播 `--quit`，切项目发 `notify project_path=`。
- **应用 → appsdk**：两个应用均一行 `bgd_appsdk::app::run(AppOptions{...})` 接入单实例/看守线程/窗口壳/日志/配置，公共逻辑零重复（03 §2 核实）。
- **editor-patch → 编辑器进程**：定位链（map_settings → tsconfig → api_pak_version）→ 整库 XOR 解密 → 插槽注入（三级回退）→ 补丁模块（目录存在即启用）→ C# 桥经 `SCE.Common.csharp_activate_window` 激活，HttpListener(127.0.0.1) 暴露 Gateway 元工具。
- **visual-injector → 触编**：启发式解析 `local M` 模块 → FunctionDefine/Class JSON（写入 `src|ui/src/data/{methods,classes}/`）+ SceInit.lua 追加/移除注册行，命名三处一致（`__bgd_<set>_<side>_<Module>`）。

## 2. 关键数据流/控制流

| 流程 | 链路 | 关键机制与风险点 |
| --- | --- | --- |
| 项目初始化 | tools → framework codeload main zip → 渲染 init/emmyrc/gitignore/AGENTS → 写入 `.bgd/` | 版本号记最新 tag 但内容是 main 快照（04 F-H1） |
| 构建 | builder.rs 白名单构建 → 静态 require 前缀改写（引号内正则）→ res 五类同步 + 字面量替换 → API 聚合 init 生成 → 入口合并（分界标记，脏数据自愈） | 改写是文本级操作（02 缺点4）；builder.rs 1030 行职责过载（01-M6） |
| 监听更新 | notify 事件 → 300ms 去重（以文件实际存在性复核删除态）→ 增量重建 | CLI watch 不写 `.watch_state.json`，check-watch 契约断裂（01-M1 / 04 F-M5） |
| 框架更新 | releases/latest 取版本号 + main 快照取内容 → 三路哈希（基准 `.framework_state.json`，文本 LF 归一）→ 更新/新增/删除/保留/冲突五分类 | 基准丢失时用 **tag 快照**重建，与 main 快照安装来源不一致 → 假冲突（04 F-H1） |
| 应用安装/自启/退出 | registry → app-release.json → asset 下载落盘 `apps/<id>/<id>.exe`；自启读 `auto_start_apps` + `default_auto_start` 播种；退出广播 `--quit` 兜底 taskkill | 落盘重命名与 editor-patch 硬编码信号前缀错配（04 F-M1）；无哈希校验（04 F-M3） |
| MCP 操作编辑器 | 宿主/AI → `sce_app_editor-patch mcp`（stdio NDJSON，恒定 8 工具）→ 本地实现（editor/logs/capture）+ 在线透传 → C# 桥 Gateway（恒定 10 元工具 + 能力目录）→ Lua 事件总线 | 桥无鉴权（03-M6）；C# dll 需先 dotnet build 且版本双注入一致（04 F-M2） |

## 3. 技术选型优缺点总评

| 选型 | 优点 | 缺点 |
| --- | --- | --- |
| **Tauri 2 + WebView2**（宿主） | 单 exe 绿色分发；Rust 后端与 CLI 共享核心函数；capabilities 权限面最小（仅 core+dialog，01 §3.8） | 强绑 Windows/WebView2；`csp: null` 无内容安全策略（01-M8）；前端构建链（pnpm）在本机沙箱不稳定 |
| **Rust 全家桶**（宿主 + SDK + 两应用） | 类型安全跨四仓库复用；appsdk 真消除重复（两应用 main 一行接入）；单文件 exe 契合应用市场分发 | 构建链多段（cargo + pnpm + dotnet）；编辑器补丁这类强平台耦合代码使 Windows API 面铺得很广 |
| **Lua 静态 require + 构建期前缀改写**（框架） | 全生态最有价值的决策：源码即真实路径，EmmyLua 全程补全/跳转可见（02 §3.1） | 文本级正则改写天然脆弱（注释/字符串中形似文本依赖工具实现自律；裸 `require('src')` 需特判）；软覆盖「游戏侧后加载」仅靠 entrance 两行书写顺序保证，无防护（02 缺点2） |
| **egui 应用壳（appsdk AppShell）** | 中文字体/项目栏/选项卡/状态栏统一；驻留方案有实测结论沉淀（egui 隐藏休眠 → 看守线程直接 Win32，03 §2） | egui 隐藏即休眠的坑需每个应用依赖 SDK 绕行；即时模式 UI 表达能力有限；窗口居中 1920x1080 硬编码兜底（03-L2） |
| **C# 进程内 MCP 桥**（editor-patch） | Gateway 恒定 10 元工具 + 能力目录，tools/list 不随能力膨胀；read/write/danger 三级 + 审计反压取舍 + 自愈 schema 反馈，面向 AI 调用方设计成熟（03 §4.3） |  dotnet build 是 cargo build 的前置且版本需双注入一致（04 F-M2）；HttpListener 仅绑 127.0.0.1 但零鉴权（03-M6）；编辑器升级需重跑 make_catalog 再重编 dll |

## 4. 架构层面优点

1. **CLI/GUI 同码路径**（01 §3.1）：CLI 子命令直接调核心函数，「测 CLI 就是测最终产物」在代码层成立，验证成本极低。
2. **SDK 消除重复是真实的**（03 §2）：Grep 验证两应用无单实例/看守线程/日志/配置的自有实现，公共逻辑演进只需改 appsdk 一处。
3. **Gateway 元工具恒定 + 能力目录**（03 §4.3）：MCP 工具面不随编辑器能力膨胀，AI 侧 prompt 稳定；invoke 参数错误内嵌 compact schema 的自愈反馈是面向 LLM 的针对性设计。
4. **失败路径均有明确语义**：三路哈希无基准时降级保守模式（01 §3.5）、入口合并脏数据自愈（01 §3.6）、监听去重以文件存在性复核（01 §3.7）、插槽三级回退失败明确报错（03 §4.2）——防御性设计贯穿全生态。
5. **发版链路自动化程度高**：四仓库 tag 触发、git log 自动归纳 release notes、app-release.json 由 CI 合成使「发版不改 registry」成立（04 §2.1 核实）。
6. **埋坑记录文化**：各仓库代码注释中的「已踩坑」结论（token 敏感头、私有 asset 直链 404、端口保留段、弹窗抑制代数令牌等）大幅降低了后续维护的试错成本（01/03 优点清单）。

## 5. 架构层面问题与风险

| # | 问题 | 证据 | 性质 |
| --- | --- | --- | --- |
| A1 | **框架版本号与内容双轨**：tag 只作版本对比、内容走 main 快照，基准重建又用 tag 快照——同一生态三种来源 | project.rs:151/162/168/421/505-507（04 F-H1） | 机制性缺陷，可致大面积假冲突 |
| A2 | **require 改写与软覆盖全靠约定**：文本级正则改写 + entrance 顺序保证软覆盖，均无检测/防护 | 02 §3 缺点 2/4；builder.rs:148-181 | 脆弱点，顺序/写法被破坏即静默失效 |
| A3 | **跨进程状态契约断裂**：`.watch_state.json` 只被 GUI 维护，CLI watch/check-watch 语义不一致 | 01-M1/D4；builder.rs:92-107（pid_alive 不校进程名） | 契约缺一半 |
| A4 | **插槽版本漂移回退覆盖不全**：第三级运行时注入只处理入口+isolation，pie_capture 在非 xdeditor-169 版本静默失效 | 03-M5（kernel.rs:416-453） | 机制脆弱点，用户无感知 |
| A5 | **宿主与应用命名契约隐式冲突**：宿主安装重命名 exe 为 `<id>.exe`，appsdk 按 exe 名推导单实例前缀，editor-patch cli.rs 硬编码旧名 → refresh 信号丢失 | 04 F-M1（apps.rs:280 / app.rs:35-40 / cli.rs:77） | 跨仓库契约未文档化 |
| A6 | **凭证与供应链单点**：github_token 明文存储且是全链路唯一凭证；应用/自我更新产物零校验；框架模板明文 API key | 01-H3/M3；02-P1；04 F-H2/F-M3 | 安全爆炸半径 = 全生态 |
| A7 | **职责过载的巨型文件**：builder.rs 1030 行 10+ 职责；editor-patch main.rs 804/kernel.rs 861 超自定约定；visual-injector core.rs 1315 行 | 01-M6；03-M4/L15 | 可维护性临界 |
| A8 | **MCP 桥本机零鉴权**：write 级能力本机任意进程可调，仅 danger 级有放行+审计 | 03-M6（McpServer.cs:186-188） | 威胁模型未明示 |
| A9 | **质量保障系于个人纪律**：仅 tools 有 CI；framework 无测试；editor-patch 集成测试无 CI 承载；文档同提交约定五仓库均执行不力（23 条偏差） | 04 F-M4、04 §1.4 | bus factor = 1 |
| A10 | **仓库边界小瑕疵**：宿主 CLI 残留 editor-patch 复制来的死命令（panic）；appsdk 脚手架模板文案自相矛盾；framework 下发文档与仓库 AGENTS 不一致 | 01-H2；03-D8；02-D3 | 演进残渣 |

## 6. 全局结论与演进建议

**结论**：BGD SCE 生态是一套**架构决策优秀、实现打磨不均、流程保障系于一人**的系统。骨架层（静态 require 改写、SDK 抽象、Gateway 桥、白名单构建、三路哈希）的每个核心决策都有清晰的问题意识和实战验证；但实现层存在确定性 bug（自我更新 404、exception.lua/deque.lua 运行时崩溃）、凭证体系失守（token 明文 + 模板 API key）、以及框架版本/内容双轨这一机制性缺陷。三份源码报告合计问题 75 个（高 7 / 中 27 / 低 35，不含 04 新增），AGENTS 偏差 23 条，流程问题 10 条（04：高 2/中 5/低 3）。

**演进建议（按优先级）**：

1. **先灭确定性故障与凭证风险**：修 01-H1（自我更新 URL）、01-H2（死命令 panic）、02-P2/P3（Lua 崩溃）、04 F-M1（refresh 前缀错配）；吊销模板 API key、token 改 DPAPI 存储。这一批全部是小改动、大收益。
2. **统一框架版本与内容来源**：发版打 tag、下载取 tag 快照，消除 main/tag/基准三来源混用（04 F-H1）；同时为应用与自我更新产物加 sha256 校验，补齐供应链最后一公里。
3. **把个人纪律沉淀为 CI 门禁**：appsdk publish 加 `cargo test`、editor-patch 加 ci.yml、framework 至少加 Lua 语法/结构静态检查；「文档同提交」约定可用 PR 模板或 lint 提醒兜底，先集中核销现有 23 条偏差。
4. **给脆弱机制加检测而非靠约定**：require 改写产物抽查校验、软覆盖顺序断言、watch 状态文件 CLI 路径补齐、插槽运行时注入覆盖 pie_capture 锚点——把「静默失效」逐个改为「明确报错」。
5. **降 bus factor**：离线恢复手册（token 清单、ci/refs 来源、发版步骤）、凭证轮换流程文档化；中期考虑 appsdk 之外再抽一层「发布工具链」统一四仓库版本注入逻辑。
