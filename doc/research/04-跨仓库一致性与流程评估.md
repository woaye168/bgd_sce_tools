## 2. 发布/版本链路核实（逐文件亲读结论）

### 2.1 五仓库 workflow 现状

| 仓库 | 文件 | 触发 | 实质 |
| --- | --- | --- | --- |
| tools | `.github/workflows/release.yml` + `ci.yml` | tag v* / main push+PR | tag 注入版本到 tauri.conf.json+Cargo.toml → tauri-action 出 NSIS 包 + git log 归纳 notes；**唯一有 CI（build+check+test）的仓库** |
| framework | `.github/workflows/release.yml` | tag v* | **只创建 Release（无任何构建/校验）**，notes 用 git log 归纳；无 `.github/release.yml` 分组文件 |
| appsdk | `.github/workflows/publish.yml` | tag v* | tag 注入 Cargo.toml → `cargo publish`（secrets.CARGO_REGISTRY_TOKEN）；无 ci.yml，无 `cargo test` 步骤 |
| visual-injector | `.github/workflows/release.yml` | tag v* | tag 注入 Cargo.toml → `cargo build --release` → **CI 合成 app-release.json**（app.json + version + release_notes）→ 上传 exe + app-release.json |
| editor-patch | `.github/workflows/release.yml` | tag v* | tag 注入 Cargo.toml → **先 dotnet build C# 桥（-p:Version 同版本，ci/refs 引用程序集）** → cargo build → 合成 app-release.json → 上传 |

已核实支撑文件：`bgd_sce_plugins/registry.json`（2 条极简条目 id/name/repo）、`sce_app_editor-patch/app.json`（含 `default_auto_start: true`）、`sce_app_visual-injector/app.json`（无 default_auto_start）、`sce_app_editor-patch/ci/refs/`（8 个引用 dll 在位）。

### 2.2 宿主侧消费链路核实（apps.rs / updater.rs / project.rs）

- **registry 拉取**：URL 硬编码在前端 `src/pages/AppPage.tsx:9`（`raw.githubusercontent.com/woaye168/bgd_sce_appsdk/main/registry.json`），后端 `fetch_registry_async` 经 net.rs 带 token 请求。
- **app-release.json 补全**：`enrich_app_async` → `repos/{repo}/releases/latest` 定位 `app-release.json` asset → `Accept: octet-stream` 下载（apps.rs:201-230）。`apply_release_meta` 仅在字段非空时覆盖，registry 原值兜底（apps.rs:149-168）。
- **安装**：tag 空或 `latest` 走 releases/latest，按 `asset_name` 定位 asset 下载，**落盘重命名为 `apps/{id}/{id}.exe`**（apps.rs:280），再写本地 app.json 记录版本（apps.rs:285-293）。
- **自我更新**：`check_self_update` 用 `SELF_REPO` 常量正确（updater.rs:36），但 `start_self_update_async` 用 `env!("CARGO_PKG_NAME")` 拼 URL **缺 owner 必然 404**（updater.rs:71，即 01-H1，本次亲读确认仍在）。
- **框架链路**：版本号取 `releases/latest` 的 tag_name（project.rs:173-184），**内容取 codeload main 分支快照**（project.rs:151, 162），基准重建取 **tag 快照**（project.rs:168）。

## 4. 文档同步约定执行情况判断

结合三份报告偏差计数：tools 7 条中 4 条是「机制已升级、文档没跟上」（D1/D4/D5/D6），framework 5 条全是文档/骨架欠账，应用生态 10 条中 6 条是注释/文档过期。「功能改动与文档同提交」约定**在所有仓库都未被稳定执行**，且偏差呈现同一模式：**机制演进 → 代码改完 → 文档/注释留在上一代**。最危险的不是 AGENTS.md 滞后（读者会存疑求证），而是 **framework 下发到每个项目的 libs/README.md 与 doc/api 过期**（02-D3/D4）——它们直接误导最终用户写代码，且随框架更新持续分发错误信息。

## 5. 结论

跨仓库协议设计本身（registry 极简条目 + app-release.json 补全、tag 注入版本、宿主/应用 CLI 契约）是**自洽且经过演进的**，R5 清单链路与三处代码核实一致。真正的流程风险集中在三点：**框架版本/内容双轨制（F-H1）是唯一可能造成大规模错误更新结果的机制性缺陷**；凭证体系（F-H2）是安全与可用性的共同单点；测试闭环（F-M4）与 bus factor（F-L3）决定了这套生态目前的质量完全依赖维护者个人纪律。建议按 F-H1 → F-H2 → F-M1 顺序处理，文档偏差按 §1.1/1.2 表逐条核销（预计一次集中提交可清掉大半）。
